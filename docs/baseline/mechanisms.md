# 非角色机制

## 设计原则

非角色机制不是新的 Agent 角色，也不拥有独立身份、日志或长期职责。它们是当前会话 Agent 在特定条件下执行的一组检查清单。

人类用户是项目 Owner（负责人），负责设定目标、接受结果与裁决异常。Agent 负责按清单执行、指出问题、记录证据；**推进依据 = 门禁结论**（BCR-015 L1）：约定名门禁 `l1-gates` 在当前 commit 绿灯 → 按清单自动推进并留痕；非绿 → 退回 Owner 确认（降级条款，见 `runtime.md` 红线）。异常与无法判断的情况一律升级 Owner。

### 关于机制写权限

非角色机制可以更新项目级状态，但不能代替其他角色写角色结论。

允许当前机制执行者更新：

- 当前角色日志。
- `docs/progress/INDEX.md` 的项目级当前状态、下一步入口和最近收尾摘要。
- 当前迭代记录中与机制直接相关的状态、证据、遗留项和关闭结论。
- 当前 ad-hoc、Change Note 或知识库索引中与本次机制直接相关的条目。

不允许当前机制执行者代写其他角色日志、替其他角色下最终专业结论，或修改跨任务待办中归属其他角色的“归属角色 / 状态”字段。需要其他角色补充时，只能登记“待该角色补充/确认”，或由 Owner 明确授权。

## 机制总表

| 机制 | 触发时机 | 谁启动 | 谁执行 | 结束条件 |
|------|----------|--------|--------|----------|
| Bootstrap 初始化 | 缺少 `docs/progress/INDEX.md` | 用户明确要求；或 Agent 检测到缺失后建议并获得用户确认 | 当前会话 Agent | 进度目录和进度索引已创建，并由用户确认 |
| 收尾归档 | 用户说收尾/下班/先停、非迭代工作完成、Change Note 执行完成、迭代关闭前后、或上下文达到归档阈值 | **迭代关闭通过后自动执行**（BCR-015 L1·S4，结果留痕不请示）；或用户明确要求 / 当前 Agent 检测到需要收尾 | 当前会话 Agent | 当前工作状态、证据、当前角色日志、索引、知识沉淀和下一步入口已更新；其他角色只登记待补充 |
| 迭代关闭检查 | DevOps（运维/部署工程师）部署通过、部署跳过且用户接受、或用户要求关闭迭代 | **部署检查通过 + `l1-gates` 绿灯时自动进入**（BCR-015 L1·S2/S3；非绿退回 Owner 确认）；或用户明确要求 | 当前会话 Agent | `INDEX.md`、迭代记录、Review 摘要、部署状态、遗留项一致（机器可判项经 CI 核对）；**Owner 验收结论已签**（通过 / 有条件通过；「打回」则禁止关闭——G5 打回闸） |
| 流程审计 | 状态混乱、角色冲突、门禁不一致、用户质疑流程、或连续两轮以上卡住 | 用户明确要求，或任一角色在日志中提出 `[基线修正提案]` | 当前会话 Agent | 输出问题清单、建议修正；涉及框架规则修改的，写 `BCR-###` 入 coordination 基线修正提案池（见 `cross-project-collaboration.md`），不在本项目直接改 `baseline/` |

## 1. Bootstrap 初始化

### 启动口令

```text
执行 Bootstrap 初始化流程。
```

### 自动建议触发

如果 Agent 启动时发现以下情况，应停止常规角色工作，并建议用户先执行 Bootstrap：

- 缺少 `docs/progress/INDEX.md`

检测到缺失时只允许建议，不能自动创建文件。用户只是问候、闲聊或询问状态时，Agent 必须等待用户确认是否执行 Bootstrap。

助手入口文件随工作流存在，不需要 Bootstrap 生成。`project-context.md` 由 PM（产品经理）在首次 PRD 时创建。角色日志由对应角色首次激活时自行创建。这些都不再作为 Bootstrap 的触发条件。

### 执行者

当前会话 Agent 执行。它不变成 Project Manager（项目经理），也不创建项目经理日志。执行前必须说明：Bootstrap 是一次性初始化机制，不是常驻角色。

### 输出

- 进度目录结构
- 初始进度索引（`INDEX.md`）
- 下一步建议：询问用户是否需要以某个角色或工作类型继续；如果不需要，保持 General（通用助手）或收尾

项目上下文、角色日志和迭代记录不在 Bootstrap 范围，由对应角色按需创建。

## 2. 收尾归档

### 启动口令

```text
执行收尾归档。
今天收尾。
这次先到这里。
```

### 自动建议触发

**迭代关闭检查通过后，收尾归档自动执行，结果留痕、不再请示**（BCR-015 L1·S4）。此外，当前 Agent 发现以下任一情况，应建议或直接执行收尾归档：

- 用户表达“今天下班”“先停一下”“收尾”“归档一下”。
- 一个非迭代工作已经完成、被中止，或需要升级为标准迭代。
- Change Note 已由受影响角色确认并完成执行。
- 迭代关闭检查通过，准备形成归档摘要。
- 当前角色日志、Review 记录或上下文达到 `context-policy.md` 的归档阈值。

### 执行者

当前会话 Agent 执行。它仍然保持当前角色，不变成 Project Manager（项目经理）。

如果收尾内容涉及其他角色边界，当前 Agent 只记录“需要谁确认/补充”，不要替其他角色下最终结论。用户可以选择切换角色、邀请对应角色补充，或接受当前记录作为阶段性收尾。

### 通用检查项

1. 判断当前工作属于：标准迭代、非迭代工作、Change Note、普通会话记录。
2. 更新当前产出物状态：进行中 / 已完成 / 已中止 / 已归档 / 升级为迭代。
3. 写入或更新验证证据、风险、遗留问题。
4. 更新当前角色日志，说明本次做了什么、没做什么、下一步从哪里继续；其他角色只登记待补充/待确认，不代写日志。
5. 更新 `docs/progress/INDEX.md`，让下次启动不用翻历史。
6. 如有长期价值，按 `knowledge-base.md` 提炼到 `docs/knowledge/`。
7. 如达到上下文阈值，按 `context-policy.md` 做摘要归档。
8. 如本次有文件变更，按 Git 安全规则提交；如没有变更，记录“不需要提交”的原因。

### 非迭代工作收尾

非迭代工作完成时，当前执行角色必须更新 `docs/progress/ad-hoc/` 中的记录：

- 最终状态：已完成 / 已中止 / 升级为迭代。
- 操作或产出摘要。
- 验证证据或未验证原因。
- 是否需要进入标准迭代。
- 是否需要沉淀到知识库。
- 下一步建议；如果需要升级为标准迭代，建议由 PM（产品经理）创建 PRD。

如果非迭代工作只是形成方案、草案或预研结论，不代表自动落地。只有用户明确要求推进时，才升级为标准迭代。

### Change Note 收尾

Change Note 的状态流转为：

```text
待确认 -> 已确认 -> 已执行 -> 已归档
```

也可以在中途转为：

```text
已废弃 / 升级为重大变更
```

规则：

1. 提出角色必须说明影响范围，并动态指定受影响角色，不按固定表机械执行。
2. 受影响角色确认后，轻量变更可以直接进入修改或开发，不重启完整 Review。
3. 执行完成后，必须更新 Change Note 的执行记录、验证证据和关联提交。
4. 如果修改了已定稿文档，必须在文档中保留 Change Note 引用或变更记录，不能静默覆盖历史结论。
5. 归档时更新迭代记录或 ad-hoc 记录中的 Change Note 索引。
6. 有长期价值的取舍、经验或风险，提炼到知识库。

### 标准迭代收尾

标准迭代完成后，不只把状态改成“已完成”，还要形成可读的归档摘要：

- 生成或更新 `docs/progress/iterations/vX.Y-summary.md`。
- 确认所有阶段状态、Review 记录、Change Note、测试和部署状态一致。
- 将未完成事项标记为延期、废弃或转入下一迭代机会。
- 更新 `docs/progress/INDEX.md`。
- 必要时更新角色 summary 和知识库。

### 输出

- 收尾结论：已完成 / 暂停待续 / 已中止 / 升级为迭代 / 需要用户确认
- 更新文件清单
- 验证证据或未验证原因
- 遗留问题和下一步入口
- 是否需要知识库沉淀

## 3. 迭代关闭检查

### 启动口令

```text
执行迭代关闭检查。
```

### 自动触发（BCR-015 L1）

以下任一情况成立且 `l1-gates` 在当前 commit 为**绿灯**时，当前 Agent **自动进入**迭代关闭检查（非绿退回 Owner 确认并登记降级留痕）；用户亦可随时口令启动：

- 部署检查已通过（Owner 验收在关闭检查内签署，不作进入前置——与机制总表口径一致）
- 部署检查被标记为已跳过，且原因已记录
- 当前迭代所有阶段均为 `已定稿` 或 `已跳过`
- 用户问“这个迭代是不是结束了”

### 执行者

当前会话 Agent 执行。若用户刚以 DevOps（运维/部署工程师）角色工作，可以顺手执行关闭检查；若用户单独要求关闭检查，则不用切换角色。关闭前须确认 Developer 自测结论与 Owner 验收结论齐备。

### 检查项

1. `docs/progress/iterations/vX.Y.md` 中各阶段状态一致。
2. PRD（含界面要点）、设计文档、实现 Review、Developer 自测报告、Owner 验收、部署检查均有结论。
3. **验收证据链核对（BCR-015 L1）**：PRD 每条验收标准在自测报告「验收证据链」表中有对应行，且状态为绿或显式标「人工抽检」（附原因）；迭代记录「验收证据链」小节指针有效。缺行或留空视为不可关闭。
4. 所有阻塞项已关闭，或明确延期并得到用户接受。
5. `docs/progress/INDEX.md` 的当前迭代状态已更新。
6. 当前角色日志、迭代记录和 Review 摘要中没有未处理的关键阻塞；其他角色日志只读摘要或登记待确认，不全文扫描。
7. Change Note 均已归档、废弃，或明确转入下一迭代。
8. 迭代摘要和知识库沉淀已完成，或写明不需要沉淀的原因。
9. 本迭代是否有后端能力废弃？若有，关闭检查执行者必须核对前端引用是否为零（详见 `role-developer.md` §跨轮契约变更同步）；涉及测试判断由 Developer 自测核对，无法判断时报 Owner。
10. 本迭代是否变更了项目定位 / 名称 / 技术栈 / 上线状态 / 工作流接入状态？若否，跳过。若是：
   - 本项目属多项目生态且已配置 / 确认 coordination → 按 `cross-project-collaboration.md` 的 coordination 发现机制与跨仓写入纪律处理（§项目元信息同步）：有写权限时在协调台账 `STATUS.md`「元信息变更台账」登记一行（项目 / 字段 / old / new / 来源）；无写权限时输出待登记行转交有权限会话；
   - 无 coordination → 在本次迭代关闭记录中登记「本次元信息变更未同步生态台账（无 coordination）」，并提示 Owner 是否建立 coordination。

### 输出

- 关闭结论：可关闭 / 不可关闭 / 有条件关闭
- 未关闭原因或延期项
- 机器可判项（**迭代记录内状态词一致 / 验收证据链齐全且取值合法 / Change Note 终态**）经 CI（`l1-gates`）核对通过后**自动更新**迭代记录、`INDEX.md` 和迭代归档摘要（BCR-015 L1·S2）；**`INDEX.md` 与迭代记录的一致性属人工核对项（检查项 5），CI 不承接**；**Owner 验收结论为关闭前置（A3 签字保留）**——通过 / 有条件通过方可关闭，「打回」则禁止任何阶段状态前进（G5 打回闸），直至出现新的验收结论
- 关闭后执行一次收尾归档，更新当前角色日志、项目索引和必要知识库；其他角色只登记待补充/待确认

## 4. 流程审计

### 启动口令

```text
执行流程审计。
```

### 自动建议触发

如果出现以下情况，Agent 应建议流程审计：

- 阶段状态互相矛盾
- Review 轮次对不上
- 某角色越权修改产出物
- 连续两轮 Review 卡在同类问题上
- 用户质疑工作流设计是否合理
- 角色日志出现 `[基线修正提案]`

### 执行者

用户明确说“执行流程审计”时，由当前会话 Agent 执行（不再设独立角色）。当前角色发现异常时，可直接做范围自检并输出问题清单。审计若发现工作流框架本身需要修改，写 `BCR-###` 入 coordination 基线修正提案池（见 `cross-project-collaboration.md`），不在本项目直接改 `baseline/`。

### 输出

- 问题清单
- 严重程度
- 建议修正
- 是否需要基线修正提案
- 若需要修改工作流框架，写 `BCR-###`（拟改文件 + 理由）入 coordination 基线修正提案池，不在本项目直接改 `baseline/`
