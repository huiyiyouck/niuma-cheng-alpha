# ADR-0002: 全量同步的时间窗自适应切片与窗口级对账

- 日期: 2026-08-15
- 状态: 提议（待 v0.1 设计文档 Review 通过后转「已采纳」）
- 关联: `docs/progress/iterations/v0.1-design.md` §4.1；PRD 验收 #1 / #10、风险 1

## 背景

平台列表 API 对未提交 Alpha 报告 `count = 10000`——这个整数可疑，可能是计数或分页上限（`brain-platform-facts.md` §1）。PRD 验收 #1 因此定了双路口径：主口径为「本地去重条数 == 时间窗切片穷尽求和的去重条数，且连续两次结果一致」，诊断项为「offset 穷尽与主口径不一致时记录『offset 封顶』留痕」。

设计时发现一个必须处理的问题：**若时间窗切片是唯一写入路径，「本地条数」与「切片求和条数」恒等**，验收会退化回 R1 意见 A4 指出的自证循环。PRD 的口径本身没错，错在把它字面实现会失去判别力。

## 决策

1. **切片算法**：按 `dateCreated` 时间戳递归二分。对窗口 `(from, to)` 先用 `limit=1` 取平台报告的 `count`；`count >= split_threshold`（默认 9000）则二分递归，否则该窗口为叶子，用 offset 分页穷尽。
2. **窗口边界重叠 1 秒**：下一窗口起点回退 1 秒，重复记录由 `alpha_id` 主键 UPSERT 去重。
3. **主口径断言落到窗口级**：每个叶子窗口断言 `实际拉取的去重条数 == 平台对该窗口报告的 count`。这才是可证伪的那一层。
4. **幂等断言**：连续两次全量同步，本地行数不变。
5. **offset 穷尽降为诊断路径**：另跑一次不带时间窗的 offset 直连穷尽，与本地行数不一致时写 `meta.offset_ceiling_detected` 留痕。断言的是**留痕存在**，不是两数相等。
6. **断点**：`sync_slice` 表记录每个窗口的完成状态，`--resume` 跳过 `status=done` 的窗口。

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|------------|
| 固定粒度切片（如每 30 天一窗） | 实现简单 | 实测样本创建时间高度集中（20 条集中在 2026-01-24~02-01，批量生成产物），固定粒度必然出现「某窗口内上万条」的热点窗 | 热点窗会再次撞上 offset 上限，等于没解决问题 |
| 先拉完再判断是否需要细分 | 不依赖 `count` 字段 | 每次试探都要付出完整分页代价 | 列表响应自带 `count`，`limit=1` 一次请求即可判断，无需试探 |
| 窗口首尾相接（不重叠） | 无重复请求 | 平台参数 `dateCreated>` 与 `dateCreated<` **两端都是开区间**，恰好等于切分点的记录会被两侧同时排除而静默丢失 | 静默丢数据是最坏的失败模式——不报错、对账还可能自洽 |
| 直接断言「本地条数 == 切片求和」 | 照 PRD 字面实现 | 切片是唯一写入路径时两数恒等，恒绿 | 自证循环，无判别力（R1-A4 的原始问题） |
| 用 offset 穷尽作主路径 | 最简单 | 疑似封顶未证伪前不可信 | 正是本 ADR 要规避的风险 |

## 后果

**正面**

- 验收 #1 真正可证伪：窗口级对账能抓出分页缺失，幂等断言能抓出重复或漏拉，封顶诊断能给出 offset 上限的实证。
- 切片按时间戳而非按天，可一路细分到秒级，对「批量生成造成的时间热点」免疫。
- 叶子窗口的 `count < 9000`，低于疑似上限 10000，因此对账左值不受封顶污染——逻辑自洽。
- 断点粒度是窗口，中断代价最多是一个窗口重来。

**负面**

- 边界重叠带来少量重复请求（每个切分点一次），代价可忽略。
- 递归切片比单路分页多出 `O(窗口数)` 次 `limit=1` 探测请求。

**风险**

- 若某窗口细分到同一秒仍 `count >= 阈值`（单秒内上万条），无法再切。此时标 `status=partial` 并留痕，用 offset 尽力拉取。实测数据分布下概率极低，但不静默忽略。
- `split_threshold` 取 9000 是基于「10000 疑似上限」的留余量估计。若平台真实上限更低，该值需下调——已做成可配置参数。
