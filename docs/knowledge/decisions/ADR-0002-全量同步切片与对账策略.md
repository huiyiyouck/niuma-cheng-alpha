# ADR-0002: 全量同步的时间窗自适应切片与窗口级对账

- 日期: 2026-08-15
- 状态: **已采纳**（2026-08-15，v0.1 设计文档 R4 两方通过并经 Owner 确认定稿）
- 关联: `docs/progress/iterations/v0.1-design.md` §4.1；PRD 验收 #1 / #10、风险 1

## 背景

平台列表 API 对未提交 Alpha 报告 `count = 10000`——这个整数可疑，可能是计数或分页上限（`brain-platform-facts.md` §1）。PRD 验收 #1 因此定了双路口径：主口径为「本地去重条数 == 时间窗切片穷尽求和的去重条数，且连续两次结果一致」，诊断项为「offset 穷尽与主口径不一致时记录『offset 封顶』留痕」。

设计时发现一个必须处理的问题：**若时间窗切片是唯一写入路径，「本地条数」与「切片求和条数」恒等**，验收会退化回 R1 意见 A4 指出的自证循环。PRD 的口径本身没错，错在把它字面实现会失去判别力。

## 决策

1. **切片算法**：按 `dateCreated` 时间戳递归二分。对窗口 `(from, to)` 先用 `limit=1` 取平台报告的 `count`；`count >= split_threshold`（默认 9000）则二分递归，否则该窗口为叶子，用 offset 分页穷尽。
2. **窗口边界重叠 1 秒**：下一窗口起点回退 1 秒，重复记录由 `alpha_id` 主键 UPSERT 去重。
3. **根窗口边界外扩 1 秒**（R2 修订）：`[T_min − 1s, T_max + 1s]`。见「R2 修订」一节。
4. **递归收敛约束**（R2 修订）：`mid` 向下取整到秒；窗口宽度 ≤ 2 秒不再细分；递归深度上限 64。
5. **主口径断言落到窗口级**：每个叶子窗口断言 `实际拉取的去重条数 == 平台对该窗口报告的 count`。这才是可证伪的那一层。
6. **全局总量交叉验证**（R2 修订）：不带任何时间窗查询得到的 `count` 与本地行数比对并留痕——独立于切片路径的第三方左值。因其可能被平台计数上限截断，只留痕、不作通过条件。
7. **幂等断言**：连续两次全量同步，本地行数不变。
8. **offset 穷尽降为诊断路径**：另跑一次不带时间窗的 offset 直连穷尽，与本地行数不一致时写 `meta.offset_ceiling_detected` 留痕。断言的是**留痕存在**，不是两数相等。
9. **断点**：`sync_slice` 表记录每个窗口的完成状态，`--resume` 跳过 `status=done` 的窗口。

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|------------|
| 固定粒度切片（如每 30 天一窗） | 实现简单 | 实测样本创建时间高度集中（20 条集中在 2026-01-24~02-01，批量生成产物），固定粒度必然出现「某窗口内上万条」的热点窗 | 热点窗会再次撞上 offset 上限，等于没解决问题 |
| 先拉完再判断是否需要细分 | 不依赖 `count` 字段 | 每次试探都要付出完整分页代价 | 列表响应自带 `count`，`limit=1` 一次请求即可判断，无需试探 |
| 窗口首尾相接（不重叠） | 无重复请求 | 平台参数 `dateCreated>` 与 `dateCreated<` **两端都是开区间**，恰好等于切分点的记录会被两侧同时排除而静默丢失 | 静默丢数据是最坏的失败模式——不报错、对账还可能自洽 |
| 直接断言「本地条数 == 切片求和」 | 照 PRD 字面实现 | 切片是唯一写入路径时两数恒等，恒绿 | 自证循环，无判别力（R1-A4 的原始问题） |
| 用 offset 穷尽作主路径 | 最简单 | 疑似封顶未证伪前不可信 | 正是本 ADR 要规避的风险 |

## 后果

**正面**

- 验收 #1 真正可证伪：窗口级对账能抓出分页缺失，幂等断言能抓出重复或漏拉，封顶诊断能给出 offset 上限的实证。
- 切片按时间戳而非按天，可一路细分到秒级，对「批量生成造成的时间热点」免疫。
- 叶子窗口的 `count < 9000`，低于疑似上限 10000，因此对账左值不受封顶污染——逻辑自洽。
- 断点粒度是窗口，中断代价最多是一个窗口重来。

**负面**

- 边界重叠带来少量重复请求（每个切分点一次），代价可忽略。
- 递归切片比单路分页多出 `O(窗口数)` 次 `limit=1` 探测请求。

**风险**

- 若某窗口细分到同一秒仍 `count >= 阈值`（单秒内上万条），无法再切。此时标 `status=partial` 并留痕，用 offset 尽力拉取。实测数据分布下概率极低，但不静默忽略。
- `split_threshold` 取 9000 是基于「10000 疑似上限」的留余量估计。若平台真实上限更低，该值需下调——已做成可配置参数。

## R2 修订（2026-08-15，设计 R1 Review 的 Developer D9/D11 触发）

初版决策有两个实现层缺陷，均由 Developer 在设计 R1 Review 中查出，已修正并记入本 ADR，不另开 ADR（决策方向不变，只是把方案补完整）：

**一、根窗口自身的开区间丢首末记录（D9，高）**

初版只处理了**窗口之间**的边界重叠，遗漏了**最外层根窗口**：定边界取到 `[T_min, T_max]` 后，窗口查询用 `dateCreated>T_min` 与 `dateCreated<T_max`，两端都是开区间，于是 `dateCreated == T_min` 与 `== T_max` 的记录被根窗口自己排除，一条都进不了库（同一秒内多条会一起丢）。

真正麻烦的是**对账发现不了**：`reported_count` 与 `fetched_count` 都由同一个开区间查询产生，左右值同源，缺失的记录既不在左值也不在右值，逐窗口比对必然全绿。这是本 ADR 立意要消除的「自证循环」在实现层的复现——我用重叠策略解决了窗口间的同类问题，却没把同一条推理应用到根窗口。

修正两条：根窗口边界外扩 1 秒（与窗口间重叠同源）；新增**全局总量交叉验证**，用不带时间窗的 `count` 作为完全独立于切片路径的第三方左值。

**二、递归在窄窗口下不收敛（D11，中）**

初版写 `split(from, mid)` 与 `split(mid − 1s, to)`。当窗口宽度为 2 秒时 `mid − 1s == from`，子窗口等于父窗口，无限递归；`mid` 在奇数秒差下的取整规则也未定义。初版写的终止条件（「切到同一秒仍超阈值则标 partial」）实际走不到——先撞上的是栈溢出。

修正三条：`mid` 向下取整到秒；窗口宽度 ≤ 2 秒不再细分；递归深度上限 64 作为兜底。

**三、口径变更的留痕（D12，中）**

本 ADR 用窗口级对账替代 PRD #1 字面主口径，属已定稿验收的通过条件变更，已按流程补走轻量 Change Note `CN-001`（`docs/progress/change-notes/CN-001-验收1主口径改为窗口级对账.md`，待 PM 确认）。技术结论不变——除恒等性外，窗口重叠还会使 `Σfetched > 本地去重行数`，按 PRD 字面写断言在实现正确时反而判红。

**教训（对后续设计的普适部分）**：「边界处理」这类推理必须显式检查**所有**边界，包括递归的根与叶。初版对相邻窗口的边界推理是对的，漏的是把同一条推理应用到自身最外层——局部正确 + 全局遗漏，且失败模式是静默的。
