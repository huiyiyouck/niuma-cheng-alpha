# ADR-0001: 技术栈与存储选型（Python + SQLite + 原始/派生双表）

- 日期: 2026-08-15
- 状态: 提议（待 v0.1 设计文档 Review 通过后转「已采纳」）
- 关联: `docs/progress/iterations/v0.1-design.md` §1.2 / §2

## 背景

v0.1 要把 1 万+ 条 Alpha 及其完整 settings / 指标 / checks 同步到本地，做规则分流、提交前预判与报告。PRD 不指定实现（前置依赖第 3 条），选型留给设计阶段。

三条硬约束框定了选择空间：

1. **本地运行、无部署**（PRD 范围边界）——不能引入需要运维的服务端组件。
2. **平台原始数据不可变、本地派生数据可重算**（PRD §5 设计约束 M4）——「备份 = 复制库文件，恢复 = 重算」。
3. **平台 API 访问收敛到可注入替身的单一客户端层**（PRD §5 设计约束）——10 项验收中 9 项标「自动」，必须能在不触达真实平台的前提下跑测试。

## 决策

- **语言**：Python 3.11+
- **存储**：SQLite（标准库 `sqlite3`），库文件 `data/inventory.db`
- **表结构**：平台原始字段与本地派生字段**分为两张表**（`alpha` / `alpha_state`）
- **原始字段**：只存 `raw_json` 一份完整响应 + 抽出少数索引/查询列，不逐字段建列
- **运行时依赖**：仅 `requests`（测试期另加 `pytest`）；CLI 用标准库 `argparse`，数据结构用 `dataclasses`

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|------------|
| JSON 文件存库存 | 零依赖、可直接看 | 无事务、无索引；断点续跑与中途崩溃下易写坏 | 断点续跑（#10）与分批预判（#6）都需要「写一条提交一条」的事务语义 |
| DuckDB | 分析查询快、列式 | 长于 OLAP、短于频繁小事务写入；额外依赖 | 本项目是「写多读少 + 事务性回写」，报告聚合量级（万行）SQLite 毫秒级即可 |
| PostgreSQL | 功能完整 | 需服务端进程与运维 | 与「本地运行、不部署」定位直接冲突 |
| 原始字段逐列展开 | SQL 直接查 sharpe 等指标 | 同一数据两处存储，可能漂移；平台加字段需改 schema | 与「平台原始不可变、单一真源」冲突；1 万条 JSON 解析在手动触发命令下是秒级，不值得用一致性风险换 |
| 派生字段同表加列 | 表少、无 JOIN | 「同步不触碰派生」只能靠代码纪律保证 | 分表让该约束由 schema 物理保证——同步流程只写 `alpha` 表，碰不到派生数据 |
| pydantic 做数据校验 | 运行时模型校验 | 额外依赖 | 外部输入只有平台 JSON，校验点集中在客户端层，dataclass 够用 |

## 后果

**正面**

- 「备份 = 复制 `data/inventory.db`」成立，无需版本化存储即满足 M4。
- 字段分层由 schema 强制，PRD §3.1 的硬约束不依赖实现者的自觉。
- 依赖面极小（1 个运行时依赖），Owner 侧无额外运行时负担。
- SQLite 事务让「每条预判结论立即落库」成本极低，断点续跑天然可靠。

**负面**

- 按指标筛选（如「找出 sharpe > 1.5 的记录」）需解析 JSON，写起来不如原生列直观。v0.1 无此需求；若 v0.2 需要，可加 SQLite 生成列 + 索引，不必改存储结构。
- 单文件库不支持多进程并发写。v0.1 是手动触发的单命令模型，不构成限制。

**风险**

- 库文件体量随 `raw_json` 增长（估算 1 万条 × ~10KB ≈ 100MB+）。`data/` 整目录 git 忽略，不进仓库；本地磁盘占用可接受。
