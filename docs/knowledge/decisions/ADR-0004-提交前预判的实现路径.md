# ADR-0004: 提交前预判的实现路径（平台接口 + 两阶段短路）

- 日期: 2026-08-15
- 状态: 提议（待 v0.1 设计文档 Review 通过后转「已采纳」）
- 关联: `docs/progress/iterations/v0.1-design.md` §4.4；PRD 验收 #6、风险 2

## 背景

PRD 验收 #6 要求对「可提交候选」执行提交前预判：分批获取相关性数据，按带来源的阈值给出三态结论（通过 / 不通过 / 待定）。口径本身在 R1 Review 后已收敛（方案 B：预判而非判定，最终裁决交平台提交结果）。

设计阶段浮现的真正约束是**成本**。Demo 深读给出了实测参数（`demo-code-deep-dive.md` §3.5）：相关性接口为平台侧异步计算，首查常返空，Demo 对其实现 **5 次重试 + 固定 20 秒间隔**——单条最坏 100 秒。若候选有数百条，逐条串行走完 self + prod 两个接口，总耗时以小时计。

同一份深读还揭示了一条可用信息：Demo 的 `brain-calculate-alpha-selfcorrQuick` skill 明确记载 **self-corr > 0.7 则 prod-corr 必然 > 0.7**，可免查平台直接判死。

## 决策

1. **走平台相关性接口**（`/alphas/{id}/correlations/{self,prod}`），不走本地 PnL 快算。
2. **两阶段短路**：先查 self；`max_corr >= 阈值` 即判 `fail`，**不再调用 prod 接口**；仅 self 低于阈值者进入 prod 查询。
3. **三态出口**：通过 → 「待确认」；不通过 → 「改造候选」；重试耗尽 → `pending`，保持「可提交候选」并加待定标注，不阻塞其余候选。
4. **阈值必带来源**：写入每条 `prediction_reason_json`，取值 `platform` / `convention_demo` / `manual`。v0.1 默认 `{"value": 0.7, "source": "convention_demo"}`。
5. **断点复用状态字段**：`prediction_result` 非空即跳过，不建独立进度表。
6. **本地 PnL 快算列为 v0.2 备选**，通过 `CorrelationResult` 返回类型稳定边界，换实现不动上层。

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|------------|
| 本地 PnL 快算（`selfcorrQuick` 路径） | 快、省平台配额；可同时算 PPAC | 需先拉全部对照集 PnL（含 88 条已提交）+ 每个候选的 PnL，引入新数据面；本地相关性算法需自行验证与平台口径一致 | PRD #6 定稿口径写明「self/prod 相关性接口」；v0.1 引入新算法的成本与验证风险都更高。边界已留好，v0.2 再评估 |
| self / prod 两路都查（不短路） | 数据更全，两个相关性值都留档 | 平台调用次数翻倍，最坏耗时翻倍 | self 超阈时 prod 必然超阈，第二次调用不产生新信息——纯浪费 |
| 并发批量查询 | 缩短总耗时 | Demo 的 `ace_lib` 证实平台有并发上限、需退避处理；并发会放大限流风险，且让断点语义复杂 | v0.1 首要目标是跑得完、可中断续跑，不是跑得快。串行 + 断点是更稳的起点 |
| 独立预判进度表 | 概念清晰 | 「已有结论就跳过」与「断点续跑」本是同一件事，两个状态载体必然漂移 | 复用 `prediction_result` 即可，少一张表 |
| 等探明平台真判定端点再做 | 结论更权威 | 端点是否存在尚未证伪，等待时间不可控 | PRD 已按方案 B 定稿；探明后经 Change Note 升级，路径已留 |

## 后果

**正面**

- 短路把最坏平台调用次数减半，且不偏离 PRD 定稿口径。
- 每条结论立即落库提交事务，任意时刻中断都不丢已完成部分。
- 阈值来源字段使「0.7 这个值从哪来」可审计——这正是 project-context「达标线动态化、不硬编码」硬约束在无平台 limit 可用时的可行落法。
- `pending` 出口让平台侧异步计算不出结果的个例不阻塞整批。

**负面**

- 总耗时仍由平台速度决定，设计侧无法再压缩。已作为风险 R-1 提请 Owner 知悉，由 Owner 决定预判范围（可先按 gap 排序只预判最优的 N 条）。
- 只查相关性，不覆盖 `DATA_DIVERSITY` / `REGULAR_SUBMISSION` / `POWER_POOL_CORRELATION`——这是 PRD 方案 B 已接受的边界，最终裁决交平台提交结果。

**风险**

- 「self > 阈值 ⇒ prod > 阈值」来自 Demo skill 的经验陈述，非平台文档保证。若该结论不成立，短路会把本可通过的候选误判为 fail。缓解：误判方向是**保守**的（把可提交的打回改造候选，不会造成误提交）；且 `prediction_reason_json.short_circuited` 字段留痕，事后可批量重置复查。

  > **证据强度说明（2026-08-15 补注）**：该结论出自 `brain-calculate-alpha-selfcorrQuick`，属 Demo 的 SOP 层（pip 包内 22 个 skills 之一）。Architect 已于同日一手通读本仓库 Demo 快照全部 10 个文件 3401 行，**确认该文件不在快照内**——通读没有、也无法验证这条结论，它至今仍是**二手**依据（转引自 `demo-code-deep-dive.md` §5，PM 下载 pip 包后所得）。若要一手验证，需下载 `cnhkmcp` 包或向平台实测。本 ADR 的决策不因通读而获得额外背书。

- 相关性接口耗时参数已一手核实并订正：`max_retries=5`、`retry_delay=20` **且无指数退避**（`platform_functions.py:1020-1036`），5 次尝试之间只有 4 次 `sleep(20)`，最坏约 **80 秒**等待而非早前估计的 100 秒。量级结论（数百条候选需十余小时）不变。
