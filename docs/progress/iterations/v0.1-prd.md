## 1. 迭代目标

把 Owner 在 BRAIN 平台的全部 Alpha 资产（实测未提交 1 万+、已提交 88）同步为**本地漏斗库存库**，用平台 checks 做**规则化分流**，产出「可提交候选清单」，并支持人工确认后提交——打通漏斗右半段（已回测 → 分流 → 提交）的最短闭环。

本迭代不做组装、不做改造 AI、不做 Web 界面、不做服务器常驻（见范围边界与版本路线）。选择先做右半段的原因：库存里已有 1 万+ 已回测 Alpha 待处理，右半段闭环是当前对「提交数」这一成功指标见效最快的一段，也为后续改造回路（v0.2）与组装核心（v0.3）提供地基（库存库 + 分流引擎是两者的共同依赖）。

## 2. 用户故事

1. 作为 Alpha 研究员，我想把平台上全部 Alpha（未提交 + 已提交）同步到本地库存库，以便完整掌握自己的资产全貌而不受平台页面筛选能力限制。
2. 作为 Alpha 研究员，我想让系统按平台 checks 结果把库存自动分流为「可提交候选 / 改造候选 / 淘汰候选」，以便不用逐个翻看 1 万+ Alpha 也知道下一步推谁。
3. 作为 Alpha 研究员，我想对「可提交候选」自动触发平台的提交前检查（相关性 / 多样性等 PENDING 类），以便确认真正可提交的最终清单。
4. 作为 Alpha 研究员，我想看到漏斗各级数量与卡点分布（哪条 check 挂得最多、差距多少），以便判断库存整体质量与后续改造方向。
5. 作为 Alpha 研究员，我想在人工确认最终清单后由系统执行提交并回写结果，以便安全地完成「筛选 → 提交」收尾（提交是对外不可逆动作，必须人工确认，不自动提交）。

## 3. 验收标准

> **验收可执行化（BCR-015 L1）**：每条验收标准必须填「验证方式」——能自动验证的填可执行命令 / 测试入口；确实无法自动验证的显式标 `人工抽检` 并写原因。**不允许留空**：标不出验证方式的验收标准本身就是 PRD 缺陷，Review 时按缺陷处理。界面类验收允许「构建通过 + 截图留档 + 人工抽检」组合，不强求端到端自动化。

| # | 验收标准（当…时，应该…） | 验证方式 | 验证入口（命令 / 测试文件路径；`人工抽检` 须附原因） |
|---|--------------------------|----------|--------------------------------------------------|
| 1 | 当执行全量同步时，应该把平台上全部未提交与已提交 Alpha 拉入本地库存库，本地条数与平台实际总数一致（含突破 count=10000 上限的完整拉取） | 自动 | 同步命令 + 对账测试（本地计数 vs 平台分页穷尽计数） |
| 2 | 当执行增量同步时，应该只拉取上次同步后新增/变更的 Alpha，且重复执行不产生重复记录 | 自动 | 幂等性测试（连续两次同步，条数与内容不变） |
| 3 | 当同步完成后，应该每条 Alpha 都带有表达式、仿真设置、指标与 checks 结果，且可按漏斗状态查询 | 自动 | 抽样字段完整性测试 + 状态查询命令 |
| 4 | 当对库存执行分流时，应该每条已回测 Alpha 被标记为「可提交候选 / 改造候选 / 淘汰候选」三者之一，且分流理由（依据哪些 check、差距多少）可查询 | 自动 | 分流命令 + 全量覆盖测试（无未分类残留）+ 理由字段非空校验 |
| 5 | 当分流规则的达标线来源于平台时，应该随 region/universe 动态读取而非硬编码，平台调整门槛后重新分流结果随之变化 | 自动 | 规则单测（注入不同 limit 的 checks 数据，断言分流结果变化） |
| 6 | 当对可提交候选触发提交前检查时，应该逐个获取 PENDING 类检查（相关性/多样性等）的最终结果并回写库存，全部通过者进入「最终可提交清单」 | 自动 | 检查触发命令 + 回写状态断言（对小批量真实候选执行） |
| 7 | 当查看漏斗报告时，应该能看到各级数量（未回测/已回测/可提交候选/改造候选/淘汰候选/已提交）与 FAIL 卡点分布 TOP 榜 | 自动 + 人工抽检 | 报告生成命令（自动断言各级数字与库存一致）；报告可读性人工抽检（原因：可读性无法自动断言） |
| 8 | 当未经人工确认时，系统不应该向平台提交任何 Alpha；当人工确认清单后，应该逐个提交、回写提交结果，失败项留明确原因 | 自动 | 提交流程测试（无确认标记时提交接口零调用；确认后模拟提交回写断言）；真实提交由 Owner 在验收时抽验 |
| 9 | 当凭据文件缺失或认证失败时，应该给出明确报错并终止，不得把凭据写入日志或库存库 | 自动 | 异常路径测试 + 日志/库文件内容扫描断言 |

## 4. 范围边界

**本迭代做：**
- 本地库存库：全量 + 增量同步（未提交 + 已提交），含表达式 / 设置 / 指标 / checks
- 规则分流引擎：按 checks 三分类（可提交候选 / 改造候选 / 淘汰候选）+ 分流理由留痕；达标线动态读取
- 提交前检查触发：对可提交候选批量触发 PENDING 类检查并回写
- 漏斗报告：各级数量 + 卡点分布（命令行 / 静态报告形态即可）
- 人工确认后的批量提交与结果回写

**本迭代不做：**
- 组装核心（生成新 Alpha）——v0.3 方向
- 改造回路（病历 → 药方，含 LLM）——v0.2 方向；v0.1 的「改造候选」只分类不改造
- Web 管理界面——漏斗报告先以命令行/静态产物承载，Web 面等库存与分流数据稳定后再建
- 服务器常驻 / 定时调度——v0.1 手动触发命令即可
- 收益追踪（Brief 已定：范围外）
- Agent Hub 接入（预留，不实现）

**版本路线（规划参考，非承诺）**：v0.1 右半段闭环（本迭代）→ v0.2 改造回路 + 常驻调度 → v0.3 组装核心 + Web 管理面。

## 6. 风险和开放问题

1. **count=10000 疑似封顶**：全量同步须验证分页穷尽策略能否突破（影响验收 #1 的「平台实际总数」口径），设计阶段需 Architect 给方案；若平台硬限制，验收口径改为「可分页获取的全部」并记录。
2. **提交前检查的配额/频率限制未知**：批量触发 PENDING 检查可能被限流，设计阶段需确认节流策略。
3. **提交动作不可逆**：已在验收 #8 强制人工确认闸；真实提交的验收由 Owner 亲自抽验。
4. **CLUSTER_TEST 含义未明**（样本中全为 ERROR）：不阻塞 v0.1（分流规则将其计为非门槛项），留待后续查证。

**A1（阻塞）· 验收 #6 缺可行 API 路径**

验收 #6 要求「逐个获取 PENDING 类检查（相关性/多样性等）的**最终结果**并回写库存」。但：

1. 已入库事实（`brain-platform-facts.md` §2 第二梯队）只记录了这些 check **初始为 PENDING**，未记录任何把它们推到最终结果的接口。
2. demo 源码中与之相关的只有 `GET /alphas/{id}/correlations/prod` 与 `/correlations/self` 两个接口，返回的是**相关性原始数据**（`schema.max`），不是平台的 check 判定；demo 的 `check_correlation()` 用**本地硬编码 0.7** 作阈值（`platform_functions.py:1136`）。
3. 该阈值来源与 project-context「达标线动态化（不得硬编码）」硬约束正面冲突——0.7 是 demo 惯例值，不是 API 返回的 `limit`。
4. PENDING 类中的 `DATA_DIVERSITY` / `REGULAR_SUBMISSION` / `POWER_POOL_CORRELATION` 三项，事实库与 demo 均无任何获取路径。

即：v0.1 核心闭环最后一环所依赖的平台能力**尚未被验证存在**。不排除平台有未探明的接口（如提交前检查触发端点），但在验证前 #6 不可承诺。

建议二选一（PM 决策，非 Architect 决策）：
- **方案 A（推荐）**：把「PENDING 检查探明」作为设计阶段的**前置 spike**（Architect 执行，非迭代预研，结论回填 PRD）。探明后按实际能力重写 #6；探明为不可得时改口径。
- **方案 B**：现在就把 #6 降级为「**预判**」口径——「对可提交候选获取相关性原始数据并回写，按记录了来源的阈值给出提交前预判；最终裁决以提交结果为准」，并把阈值来源（平台值 / 惯例值 / 手工配置）作为必填字段写进验收，以满足「不硬编码」的可审计要求。

**A2（高）· 漏斗状态枚举不自洽**

同一份 PRD 出现三套状态口径：#4 是三分类（可提交候选 / 改造候选 / 淘汰候选），#6 引入第四态「最终可提交清单」，#7 的报告要求六级（未回测 / 已回测 / 可提交候选 / 改造候选 / 淘汰候选 / 已提交）。数据模型只能有一套枚举，这直接决定库存库的状态字段设计。

另外「未回测」一级在 v0.1 **没有数据来源**：库存全部来自平台已有 Alpha 列表，而平台上的 Alpha 均为仿真产物、自带 `is` 指标与 checks；组装（产生未回测 Alpha 的唯一来源）明确排除在本迭代外。该级恒为 0。

建议：PM 给出**唯一的漏斗状态枚举 + 迁移条件**（谁→谁、由哪个动作触发），三条验收统一引用；「未回测」要么删除，要么注明「v0.1 恒为 0，为 v0.3 组装预留」。

---

**A3（高）· 分流规则对非 PASS/FAIL 结果未定义**

`result` 有五种取值（PASS / FAIL / WARNING / ERROR / PENDING），而 #4 是硬验收：「每条已回测 Alpha 被标记为三者之一，**无未分类残留**」。当前 PRD 只在风险 4 单点处理了 `CLUSTER_TEST`（计为非门槛项），没有给出普遍规则。实测中 `UNITS` 常为 WARNING、`CLUSTER_TEST` 样本全为 ERROR，这不是边缘情况。

规则不完备则「无未分类残留」不可达，或者实现方会自行编造默认值——这是最该由 PRD 而非 Developer 决定的口径。

建议：PM 明确「五种 result 各自如何计入分流」的普遍规则（例如：只有 FAIL 计门槛不达标，WARNING/ERROR/PENDING 一律计为非门槛项且在分流理由中单独留痕），CLUSTER_TEST 由普遍规则覆盖，风险 4 相应降为观察项。

---

**A4（高）· 验收 #1 的验证方式自证循环**

#1 要求「本地条数与**平台实际总数**一致」，验证方式是「本地计数 vs **平台分页穷尽计数**」。当同步实现本身就是分页穷尽时，两个数字必然相等——无论平台是否在 10000 处封顶，该验收恒为绿灯，**不可证伪**，无法回答风险 1 想回答的问题。

可用事实：列表 API 支持 `dateCreated>` / `dateCreated<` 时间窗过滤（`platform_functions.py:504-507`），这提供了一条**独立于 offset 分页的对账路径**，也是绕过 offset 上限的可行技术方案。

建议：
- 验收口径改为可证伪的表述：「按 offset 分页穷尽的条数 == 按 dateCreated 时间窗切片求和的条数」，两路不一致即判定 offset 存在封顶并留痕；
- 「平台实际总数」这一无法独立观测的口径删除，或降级为 Owner 人工抽检项；
- 若时间窗切片求和 > 10000，风险 1 即被证伪，同步策略以时间窗切片为准（这也是我在设计阶段的倾向方案）。

---

**A5（高）· 增量同步的「变更」维度无实现依据**

#2 要求「只拉取上次同步后**新增/变更**的 Alpha」。列表 API 已验证的过滤参数只有 `dateCreated>/<` 与 `dateSubmitted>/<`，**没有 dateModified 或等价的修改时间过滤**。因此「新增」可增量，「变更」（checks 重算、指标更新、属性修改）**无法增量识别**，只能靠周期性全量重拉比对。

#2 的验证方式（幂等性测试）只能覆盖「重复执行不产生重复记录」，覆盖不到「变更被正确识别」——验收与标准本身不匹配。

建议：PM 明确增量语义。倾向表述：「增量同步 = 按创建时间拉新增；变更通过全量重拉刷新，且重复执行幂等」。若确需变更增量，需先探明平台是否存在修改时间字段（可并入 A1 的 spike）。

---

**A6（中）· 「人工确认」的载体未定义**

#8 是本迭代唯一的不可逆动作闸门（对应 project-context 硬约束「提交不可逆」），但 PRD 未定义人工确认的**形态**：命令行交互输入、独立的确认清单文件、还是清单指纹签名。这不是实现细节——它决定「确认标记」能否被绕过、能否被误复用（例如确认了清单 A 却提交了变更后的清单 B），也决定 #8 前半句「无确认标记时提交接口零调用」怎么测。

建议：PM 给出确认载体与**确认对象绑定方式**（推荐：确认针对具体清单内容的指纹，清单变化则确认失效）。架构侧的可注入客户端替身由我在设计阶段承接，不需要 PRD 展开。

---

**A7（中）· 提交前检查的批量执行成本未落到验收或范围**

风险 2 已识别限流风险，但没有任何验收或范围条款承接它。已知事实：相关性接口是**逐 Alpha 调用**，且 demo 对其实现了「空响应重试 + 退避等待」（`platform_functions.py:1016-1135`），说明平台侧为异步计算、首次调用常返回空。若「可提交候选」有数百条，#6 会变成一个耗时不可控的长任务。

不写进 PRD 的直接后果是：实现阶段大概率产出一个跑几小时、中断即重来的脚本。

建议：#6 补充可控性口径——「分批执行、单批规模可配、支持中断后断点续跑、已获取结果不重复请求」，并作为验收的一部分。

---
