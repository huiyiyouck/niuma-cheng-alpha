## 1. 概述

### 1.1 设计目标与边界

实现 PRD v0.1 定稿的漏斗右半段闭环：**同步 → 分流 → 预判 → 报告 → 确认提交**。五条命令、一个本地库、一个 HTTP 出口。

本设计只解决 PRD 范围内的问题。不为 v0.2（改造回路 / 常驻调度）和 v0.3（组装 / Web）预建抽象，只在**代价为零的地方**留出接口边界（§6.2 列明是哪几处，以及为什么这几处不算过度设计）。

### 1.2 技术选型

| 维度 | 选型 | 理由 |
|------|------|------|
| 语言 | Python 3.11+ | 平台调研与 Demo 均为 Python，`requests` 生态与已验证的调用面可直接复用；Owner 侧无第二语言运行时负担 |
| 存储 | SQLite（标准库 `sqlite3`） | 1 万+ 条 × 完整 JSON 的量级下仍是单文件、零运维；事务保证断点续跑的一致性；「备份 = 复制单文件」正是 PRD 设计约束（M4）要的形态 |
| HTTP | `requests` | Demo 已验证的调用面（认证 / 列表 / 相关性 / 提交）全部基于它；v0.1 全串行，不需要异步 |
| CLI | 标准库 `argparse` | 五条子命令，无需第三方框架 |
| 数据结构 | 标准库 `dataclasses` | 不引入 pydantic：v0.1 的外部输入只有平台 JSON，校验点集中在客户端层，运行时模型校验收益不抵依赖成本 |

**运行时依赖只有 `requests` 一个**（测试期另加 `pytest`）。选型详见 `docs/knowledge/decisions/ADR-0001-技术栈与存储选型.md`。

### 1.3 模块地图

```text
alpha_platform/
├── cli.py          子命令入口、参数解析、退出码（§3.2 契约）
├── config.py       配置解析：默认值 → 配置文件 → 环境变量 → 命令行参数（后者覆盖前者）
├── credentials.py  凭据加载（BRAIN_CREDENTIALS_PATH 可覆盖，默认项目根）
├── client.py       BrainClient：★ 全项目唯一 HTTP 出口，可注入替身（§3.1 契约）
├── db.py           连接管理、schema 建表、schema_version 校验
├── sync.py         全量（时间窗自适应切片）/ 增量同步、窗口级对账、断点
├── classify.py     分流引擎：核心为纯函数，不碰 IO
├── precheck.py     提交前预判：两阶段短路、分批、跳过已有结论
├── report.py       漏斗报告（text / json）
└── submit.py       dry-run / 指纹确认 / 提交 / 快照落盘
```

模块划分对齐 Developer R1 估算的五个可独立自测单元（客户端 / 同步 / 分流 / 预判 / 报告+提交），另拆出 `db`、`config`、`credentials` 三个无业务逻辑的基础件。

### 1.4 运行产物布局（DevOps N2）

```text
data/                       ← 统一运行产物目录，整目录 git 忽略
├── inventory.db            库存库（SQLite；含库存、派生状态、断点）
├── logs/                   运行日志（R2/N7）
│   └── alpha-20260815.log
└── snapshots/              提交清单快照，一次提交一个文件
    └── 20260815-143022-a3f1b8c2.json
```

实现阶段首个 commit 前，`.gitignore` 追加 `data/`。快照落文件而非入库：它是**归档证据**，需要能被单独复制、审计、离线保留，不应随库文件重算或迁移而变动。

**日志落盘位置（R2 新增，DevOps N7）**：日志按天落 `data/logs/alpha-YYYYMMDD.log`，同时输出 stderr。定这个位置是为了给 PRD #9 一个**确定的断言对象**——#9 的验证方式是「日志与库存文件的结构化扫描断言」，扫描目标必须可寻址。随 `data/` 一并 git 忽略，无误提交风险。日志内容口径见 §4.7（白名单式）。

## 2. 数据模型

库文件：`data/inventory.db`。四张表。字段分层（PRD §3.1 Q2/M4）**由 schema 强制**而非靠代码纪律——同步流程只写 `alpha` 表，物理上碰不到已有的派生数据。

> **唯一例外：初始态创建（R2 新增，Developer D10）。** 同步须在写入 `alpha` 的同一事务内，对 `alpha_state` 执行 `INSERT ... ON CONFLICT DO NOTHING`——**只在行不存在时创建初始态，永不覆盖既有派生数据**。这不违反字段分层：PRD §3.1 规定「已回测 = 同步入库的初始态」且「stage=OS 的平台 Alpha 同步入库时直接置『已提交』」，若同步完全不碰 `alpha_state`，88 条已提交记录将永远没有状态、验收 #7 的各状态计数从第一天起就是错的。「不覆盖」才是字段分层要保护的东西，「不创建」不是。详见 §4.2。

### 2.1 `alpha`（平台原始字段，同步 UPSERT，不可变语义）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `alpha_id` | TEXT | PRIMARY KEY | 平台 Alpha ID |
| `stage` | TEXT | NOT NULL | `IS`（未提交）/ `OS`（已提交） |
| `date_created` | TEXT | NOT NULL, INDEX | ISO8601；增量水位与时间窗切片的键 |
| `date_submitted` | TEXT | NULL | 仅 OS 有值 |
| `expression` | TEXT | NOT NULL | 表达式（`regular.code`） |
| `raw_json` | TEXT | NOT NULL | ★ 列表项完整响应原样保存（含 settings / is 指标 / is.checks） |
| `fetched_at` | TEXT | NOT NULL | 本次拉取时间（UTC ISO8601） |

**设计取舍：settings / metrics / checks 不单独建列，只存 `raw_json` 一份。** 平台列表 API 每项自带完整 settings + code + is 指标 + checks（`brain-platform-facts.md` §4），拆列会让同一份数据在库中存在两处、可能不一致，而「平台原始字段不可变」要的恰恰是单一保真源。`checks` 每次分流时从 `raw_json` 解析——1 万条 JSON 解析在手动触发的命令里是秒级，不值得用一致性风险去换。上方五个抽出列只服务于**索引与查询**（主键、增量水位、状态查询），不构成第二份真源。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `alpha_id` | TEXT | PK, FK→`alpha` | |

| `status_source` | TEXT | NOT NULL DEFAULT 'sync' | ★ R2 新增（Q5）：当前状态的来源，`sync` / `classify` / `prediction` / `submit`。使报告能区分「因 checks 归入改造候选」与「因相关性预判归入改造候选」 |
| `is_pending_flag` | INTEGER | NOT NULL DEFAULT 0 | 预判「待定」标注（PRD §3.1：待定不是独立状态，是「可提交候选」上的标注） |
| `classified_at` | TEXT | NULL | |

| `classify_rule_version` | TEXT | NULL | ★ A10：分流规则版本号 |

`classify_threshold` 与 `classify_rule_version` 既单独建列又出现在 `classify_reason_json` 里：单列供 SQL 直接筛选与断言（「用旧规则版本分流的还剩多少条」），JSON 存完整明细。这处冗余是有意的，两者同一次写入、不存在漂移窗口。

**行创建时机（R2 新增，D10）**：`alpha_state` 行**只由同步创建**，与 `alpha` 行一一对应、同事务写入（§4.2）。因此 `funnel_status` 恒非空——这一条同时消除了 §4.3 适用域的 SQL NULL 陷阱（`NULL NOT IN (...)` 求值为 NULL 而非真，会把记录静默排除在分流之外）。守恒断言见 §4.3。

**生命周期（DevOps N3）**：本表是**临时派生数据**，不属于 §3.1 的字段分层两类中的任何一类。可随时清空；清空后果仅为「下次全量同步从头切片重跑」，因入库为 UPSERT，不产生重复记录、不影响库存正确性与派生数据重算能力。备份时可不含本表。

| 键 | 说明 |
|----|------|

## 3. 接口契约

> 本节是隔离会话之间的交接带宽。实现会话只读此处，不回问上游。

### 3.1 `BrainClient` —— 全项目唯一 HTTP 出口

PRD §5 设计约束要求「平台 API 访问收敛到可注入替身的单一客户端层」。**除本类外，任何模块不得直接发起 HTTP 请求**；这是 #5 / #6 / #8 / #9 能在不触达真实平台的前提下自动验证的唯一前提。

```python
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Credentials:
    email: str
    password: str = field(repr=False)   # ★ repr=False 是契约的一部分，不是实现细节（R2/N6）
    # 仅存在于内存；永不写回任何文件（Demo 弱点 1 的反面）
    # repr=False 封堵白名单式日志管不到的泄露路径：未捕获异常的 traceback、
    # logging.exception、调试器打印局部变量时的 repr 输出。
    # 配套断言（#9）：assert "password" not in repr(credentials_instance)

@dataclass(frozen=True)
class AlphaListPage:
    count: int             # 平台对该查询条件报告的总数
    items: list[dict]      # 原样 JSON 列表项

@dataclass(frozen=True)
class CorrelationResult:
    max_correlation: float | None   # None = 重试耗尽仍无数据
    attempts: int
    raw: dict | None

@dataclass(frozen=True)
class SubmitOutcome:
    ok: bool
    error: str | None      # 失败原因原文，不吞异常
    raw: dict | None

class BrainClient:
    def __init__(self, credentials: Credentials, *,
                 session: requests.Session | None = None,
                 base_url: str = "https://api.worldquantbrain.com",
                 retry: RetryPolicy | None = None) -> None: ...

    def list_alphas(self, *, stage: str, limit: int, offset: int,
                    date_created_gt: str | None = None,
                    date_created_lt: str | None = None,
                    order: str = "dateCreated") -> AlphaListPage: ...

    def get_alpha(self, alpha_id: str) -> dict: ...
    # ★ R4 新增（D21/N14）：按 ID 直查单条平台详情，返回原样 JSON（含 stage / dateSubmitted）。
    # 供 submit --reconcile 取平台真实状态——判据必须绕开本地库与水位逻辑，
    # 恢复路径不该依赖那条可能已经出问题的常规写入链。

    def get_self_correlation(self, alpha_id: str) -> CorrelationResult: ...
    def get_prod_correlation(self, alpha_id: str) -> CorrelationResult: ...
    def submit_alpha(self, alpha_id: str) -> SubmitOutcome: ...
```

#### 3.1.0 依赖注入契约（R2 新增，Developer D13）

并行实现前必须钉死的一处，否则三个业务模块会各自发明一套注入方式：

- **业务模块一律以 `client: BrainClient` 作为显式参数接收**（`sync(client, db, ...)`、`precheck(client, db, ...)`、`submit(client, db, ...)`）。**不建模块级单例、不用全局变量**——Demo 用的正是模块级单例 `brain_client`，那让替身注入只能靠 monkey-patch。
- 组装点唯一：`cli.py` 构造 `BrainClient` 并传入各业务函数。
- **测试替身以「客户端方法层」为准**：子类或同签名替身对象覆写 `list_alphas` / `get_alpha` / `get_*_correlation` / `submit_alpha`（★ R4 定稿前补 `get_alpha`，N16——本枚举是 `BrainClient` 公开方法的**穷举**，新增方法时必须同步，否则 §8 第 6 条第 6 项的 reconcile 用例无处落脚）。这是 #5 / #6 / #8 / #9 自动验证的默认写法。
- `session: requests.Session | None` 注入点保留给**需要验证 HTTP 细节的少数用例**（认证自愈、重试退避、429 处置），不作为业务测试的常规手段。

两个注入层次不可混用：`#8` 的「提交接口零调用」断言写在方法层（断言替身的 `submit_alpha` 调用次数为 0），不写在传输层。

**平台端点映射**（均已在 Demo 中验证存在）：

| 方法 | HTTP | 路径 | 备注 |
|------|------|------|------|
| `list_alphas` | GET | `/users/self/alphas` | 参数 `stage / limit / offset / order`，时间窗用 `dateCreated>` `dateCreated<` |
| `get_alpha` | GET | `/alphas/{id}` | R4 新增。Demo 的 `get_alpha_details`（`platform_functions.py:347-357`）即此端点，`brain-platform-facts.md` §2 亦有记录，双重确认 |
| `get_self_correlation` | GET | `/alphas/{id}/correlations/self` | 平台异步计算，首查常返空 |
| `get_prod_correlation` | GET | `/alphas/{id}/correlations/prod` | 同上 |
| `submit_alpha` | POST | `/alphas/{id}/submit` | ★ 唯一不可逆动作 |
| （内部）认证 | POST | `/authentication` | Basic Auth → JWT 存 cookie `t` |
| （内部）探活 | GET | `/authentication` | 见 §3.1.1 |

#### 3.1.1 认证自愈

每个公开方法进入时先 `_ensure_authenticated()`：检查 cookie 存在 → GET `/authentication` 探活 → 失效则用内存中的凭据重新认证。这直接采纳 Demo 已验证的模式（`demo-code-deep-dive.md` §3.1），**并因此关闭 PRD 风险 5 的 session 半边**：无需实测 session 生命周期，按需重认证即可覆盖长任务中途失效。

与 Demo 的差异（凭据纪律）：凭据只从 `.brain_credentials` 读入内存，**绝不回写任何文件**；日志中不出现 email / password / Authorization 头 / cookie 值。Demo 认证成功后回写明文凭据到 `user_config.json`，是我们明确不采纳的做法。

生物识别分支（Demo 用 playwright 开浏览器扫脸）**不实现**：v0.1 遇 `WWW-Authenticate: persona` 直接抛 `AuthError` 并提示 Owner 手工处理，不引入浏览器依赖。

## 4. 核心流程

### 4.1 全量同步：时间窗自适应切片（PRD #1 / #10）

PRD 主口径是「本地去重条数 == 时间窗切片穷尽求和的去重条数」。**若切片是唯一写入路径，这两个数字恒等，验收会退化回 R1 A4 指出的自证循环。** 因此本设计把主口径落到**窗口级对账**上——它才是可证伪的那一层：

```text
0. 全局总量交叉验证（★ R2 新增，D9）：
     total = list_alphas(stage, limit=1, offset=0).count       ← 不带任何时间窗，独立于切片路径
     该值作为对账的第三方左值，与本地行数比对并留痕

1. 定边界：limit=1 分别按 order=dateCreated / -dateCreated 取首末条 → [T_min, T_max]
   ★ 外扩一秒：root_from = T_min - 1s, root_to = T_max + 1s   （R2 新增，D9）

2. 递归切片 split(from, to, depth):
     page = list_alphas(stage, limit=1, offset=0, dateCreated>from, dateCreated<to)
     若 page.count >= split_threshold(9000) 且 (to - from) > 2s 且 depth < MAX_DEPTH(64)：
         mid = from + floor((to - from) / 2)        ← ★ 向下取整到秒（R2/D11）
         split(from, mid, depth+1) ; split(mid - 1s, to, depth+1)    ← 重叠 1 秒
     否则：该窗口为叶子 → 记 reported_count = page.count → 进入步骤 3
            若 count >= 阈值仍无法细分（窗口 ≤ 2s 或触达深度上限）→ status = partial 并留痕

3. 叶子窗口穷尽：offset 从 0 步进 page_size 拉完 count 条 → UPSERT 入 alpha 表
   ★ page_size 默认 100，可配（R3）：Demo 的 value_factor_trendScore 以 limit=500
     调用同一端点（platform_functions.py:635），实测该端点至少支持 500；
     调到 500 可把 1 万条的请求数从约 100 次降到约 20 次
   → 记 fetched_count = 该窗口去重 alpha_id 数 → sync_slice.status = done
   ★ 同事务对 alpha_state 执行 INSERT ... ON CONFLICT DO NOTHING 建初始态（D10，见 §4.2）

4. 窗口级对账（★ 主口径断言）：每个叶子窗口 fetched_count == reported_count
5. 全局对账（★ R2 新增，D9）：本地行数 == 步骤 0 的 total（不等则留痕，见下）
6. 幂等断言：连续两次全量同步，alpha 表行数不变
7. offset 封顶诊断：另跑一次不带时间窗的 offset 直连穷尽 → offset_count
   若 offset_count != 本地行数 → 写 meta.offset_ceiling_detected 留痕（断言留痕存在，不断言两数相等）
```

**R2 修订说明（Developer D9）：原步骤 1 会静默丢失时间轴两端的记录。** 平台参数两端都是开区间，`dateCreated == T_min` 与 `== T_max` 的记录被根窗口自身排除，一条都进不了库（同一秒内多条会一起丢）。更严重的是**对账发现不了**：`reported_count` 与 `fetched_count` 都由同一个开区间查询产生，左右值同源，缺失的记录既不在左值也不在右值，逐窗口比对必然全绿——正是 PRD R1 A4/D6 一路想根除的自证循环在实现层复现。修正为两条：根窗口边界外扩 1 秒（与相邻窗口重叠 1 秒同源，同样由主键 UPSERT 去重兜底）；新增步骤 0 的**全局总量交叉验证**，用不带时间窗的 `count` 作为完全独立于切片路径的第三方左值。

步骤 5 的全局对账不一致时**不判红、只留痕**：`total` 自身可能被平台计数上限截断（未提交实测恰为 10000），它是诊断信号而非通过条件。真正的通过条件仍是步骤 4 的窗口级对账 + 步骤 6 的幂等。

**边界重叠 1 秒的原因**：平台参数是 `dateCreated>` 与 `dateCreated<`，两端都是**开区间**。若相邻窗口首尾相接，恰好等于切分点的记录会被两侧同时排除而**静默丢失**。让下一窗口起点回退 1 秒，边界记录被拉两次，再由 `alpha_id` 主键 UPSERT 去重——PRD 主口径写的正是「**去重**条数」，与该策略天然契合。

**递归收敛（R2 新增，D11）**：原写法在窄窗口下不收敛——`to - from = 2s` 时 `mid - 1s == from`，子窗口等于父窗口，先撞上的是无限递归而不是「切到同一秒」的终止条件。三条约束：`mid` 向下取整到秒；窗口宽度 ≤ 2 秒不再细分；递归深度上限 64 作为兜底。触达任一条件仍超阈值时标 `partial` 留痕，用 offset 尽力拉取。切分按**时间戳**而非按天，可一路细分到秒级——实测样本创建时间集中在 2026-01-24~02-01（批量生成产物），单日过万并非不可能，按天粒度必然出现热点窗。

**关于 PRD #1 主口径的口径关系（R2 说明，Developer D12）**：PRD 定稿的 #1 主口径是「本地去重条数 == 时间窗切片穷尽求和的去重条数」。该口径在本设计下**不可直接作为断言**——切片是唯一写入路径时两数恒等（无判别力），且因窗口重叠 1 秒，`Σfetched_count > 本地去重行数`，按字面写断言反而会误判红。窗口级对账用平台报告的 `count` 作独立左值，是严格更强的口径。这属于已定稿验收的通过条件变更，已按流程走 **Change Note `CN-001`**（`docs/progress/change-notes/CN-001-验收1主口径改为窗口级对账.md`，待 PM 确认）。实现会话以 Change Note 确认后的口径为准；未确认前，验收 #1 的期望值以本节步骤 4 为准。

**为什么用 `count` 而不是拉完才知道**：列表 API 响应带 `count` 字段（`brain-platform-facts.md` §1 即由此得出「未提交 10000」），`limit=1` 一次请求即可判断是否需要细分，无需试探性拉取。

**断点（#10）**：`sync_slice` 中 `status=done` 的窗口在 `--resume` 时直接跳过。中断后重跑只重做未完成窗口。

### 4.2 增量同步（PRD #2）

读 `meta.last_sync_date_created:{stage}` 作为水位，`dateCreated>水位` 拉取，UPSERT，更新水位。增量语义严格等于「新增」——已入库 Alpha 的平台字段刷新由全量重拉或预判回写承担（PRD #2 定稿口径）。幂等由 UPSERT + 水位单调保证。

**初始态创建（R2 新增，D10）**：全量与增量同步都必须在写 `alpha` 的**同一事务**内执行：

```sql
INSERT INTO alpha_state (alpha_id, funnel_status, status_source)
VALUES (?, ?, 'sync')
ON CONFLICT (alpha_id) DO NOTHING;     -- ★ 只创建，永不覆盖
```

初始态映射：`stage = 'IS'` → 「已回测」，`stage = 'OS'` → 「已提交」（PRD §3.1 明文规定）。

`DO NOTHING` 是这条的关键：本地已提交成功的记录下次同步时 `stage` 变为 OS，其派生状态「已提交」不被触碰；本地「提交失败」的记录在平台上仍是 IS，其状态同样不被回退。**「不覆盖」才是字段分层保护的东西，「不创建」不是**——两者混同会让 88 条已提交记录永远没有状态。

### 4.3 分流（PRD #4 / #5，§3.2 规则）

核心是**纯函数**，不碰 IO——这是 #5「注入不同 limit 的 checks 数据断言分流结果变化」能被单测覆盖的前提：

```python
RULE_VERSION = "v1"

def classify_checks(checks: list[dict], threshold: float) -> ClassifyResult:
    """输入 is.checks[] 与改造阈值，输出状态与理由。无 IO、无全局状态、可重复调用。"""
```

判定逻辑严格照 PRD §3.2：

1. 门槛项 = `result ∈ {PASS, FAIL}`；`WARNING / ERROR / PENDING` 一律非门槛，进 `non_gate` 留痕但不参与判定
2. `gap = |value − limit| / |limit|`；`value` 或 `limit` 缺省、或 `limit == 0` → 标 `quantifiable: false`，按「差距在阈值内」处理（保守归改造候选）
3. 无 FAIL → 可提交候选；全部可量化 FAIL 的 gap ≤ 阈值 → 改造候选；任一 > 阈值 → 淘汰候选

**适用域（PRD §3.2 D5/A11，R2 修订）**：

```sql
-- 适用域只排除保护态。★ R3：不在 SQL 里判断 prediction_result（D16）
-- 因 alpha_state 行由同步创建（§4.2）且列 NOT NULL，funnel_status 恒非空
WHERE funnel_status NOT IN ('待确认', '已提交', '提交失败')
```

**写回逻辑（R3 新增，D16/D17 合并处置）**：适用域内的每条记录都参与重算，但写回时分两种：

```python
locked = (row.prediction_result == 'fail')   # Python 比较：None == 'fail' 为 False，无三值逻辑
if locked:
    # 预判判死的记录：状态与来源锁定，但理由照常刷新
    write(funnel_status='改造候选', status_source='prediction',
          classify_threshold=..., classify_rule_version=..., classify_reason_json=...)
else:
    write(funnel_status=<按 §3.2 规则判定>, status_source='classify',
          classify_threshold=..., classify_rule_version=..., classify_reason_json=...)
```

三处 R2/R3 修订：

**① NULL 陷阱已从根上消除（D10）。** SQL 中 `NULL NOT IN (...)` 求值为 NULL 而非真——若 `alpha_state` 行不存在或状态为空，这些记录会被静默排除在分流之外，而验收 #4 的「无未分类残留」检查只看结果集内部，查不出被排除的记录，又是一条会亮绿灯的失败路径。解法不是在 WHERE 里打补丁，而是让 `funnel_status` 恒非空：行由同步创建（§4.2）、列声明 NOT NULL。配套**守恒断言**（写进 #4 的全覆盖测试）：

```text
alpha 表行数 == alpha_state 表行数
             == 已回测行数 + 三类候选行数 + 保护态行数     ← ★ R3/D20：补「已回测」
```

补「已回测」后该断言**恒成立**（含刚同步、尚未分流的状态）。R2 版漏了这一态，只在 `classify` 已覆盖全库时才成立，刚同步即跑断言必然失败。

**② 预判为 `fail` 的记录保持「改造候选」（D14）。** A9 保住了预判**结论**（重算不清空 `prediction_*`），但没保住结论在**状态层的后果**：一条因相关性超阈被打回「改造候选」的记录，其 checks 本就无 FAIL，重跑 `classify` 会把它算回「可提交候选」；而 `prediction_result` 非空又让 `precheck` 永久跳过它——它既进不了「待确认」、也不在提交清单里，报告里却以「可提交候选」示人，误导 Owner 以为它可推进。PRD §3.1 明写改造候选的进入条件之一就是「或提交前预判不通过」，保持该状态是对 PRD 的忠实实现，不是新口径。

**③ 该判断必须在写回逻辑里做，不能写进 WHERE（R3 修订，D16/D17）。** R2 版把它写成适用域的第二个条件 `AND NOT (funnel_status = '改造候选' AND prediction_result = 'fail')`，踩了与 D10 同型的 NULL 陷阱、且方向相反：当 `prediction_result` 为 NULL 时，`NULL = 'fail'` → NULL，`TRUE AND NULL` → NULL，`NOT NULL` → NULL，该行被 WHERE **静默丢弃**。被丢弃的恰恰是「因 checks FAIL 归入改造候选、从未预判」的记录——**改造候选的主体**。（`('淘汰候选', NULL)` 等因首项 FALSE 短路不受影响，所以问题只集中在改造候选上。）

后果：`classify --threshold` 调整后绝大多数改造候选不参与重算，**验收 #5「平台调整门槛后重新分流结果随之变化」对改造候选整体失效**；而守恒断言仍然成立（记录还在「改造候选」里，只是没被重算）——第五条「亮绿灯但数据错」的路径。

R3 的修法不是给 SQL 补 `ifnull()`，而是**把判断移出 SQL**：适用域只排保护态（无 NULL 参与），`fail` 判断放到 Python 写回逻辑（`None == 'fail'` 为 False，二值逻辑，无陷阱）。这样同时解决 D17 指出的正文与 SQL 矛盾——记录参与重算，`classify_*` 照常刷新（理由要新），只锁定 `funnel_status` 与 `status_source='prediction'`（状态与来源要真）。

> 通用教训（与 D10 同源）：**凡是在 WHERE 里用条件表达式处理可空列，就还会再踩一次。** 能在 schema 上消除 NULL 的就消除（D10 的 NOT NULL），不能消除的就把判断挪出 SQL（本条）。

重算只覆盖 `funnel_status` / `status_source` / `classify_*`，**不触碰 `prediction_*`**（A9）。

**`is_pending_flag` 归预判侧（R4 新增，Q7 答复）**：该列与 `prediction_*` 同属预判侧，重算**不触碰**。相应地，§4.5 第 4 块「待定条数」的统计口径必须限定为 `is_pending_flag = 1 AND funnel_status = '可提交候选'`——否则一条被标待定的记录在阈值调紧后重算为「淘汰候选」，仍会被计入待定数，并提示 Owner 用 `--retry-pending` 去重试一条已经不是候选的 Alpha。

每次写入必带 `classify_threshold` 与 `classify_rule_version`（A10）：任一历史分流结论都能被解释和重现。

### 4.4 提交前预判：两阶段短路（PRD #6）

**成本是本流程的核心约束。** 相关性接口最坏约 **80 秒**等待/条——`max_retries=5` 时 5 次尝试之间只有 **4 次** `sleep(20)`，且无退避递增（`platform_functions.py:1020-1036`，2026-08-15 一手核验；R4 订正，此前误记为 100 秒，见 §7.1 R-1）。据此设计两阶段短路：

```text
候选集 = (                                                     ← ★ R3/D18：补括号
           funnel_status == '可提交候选'
           AND ( prediction_result IS NULL                     ← A9 跳过已有结论
                 OR (--retry-pending 且 prediction_result == 'pending') )   ← R2/D15
         )
         OR (                                                  ← ★ R3/D18：加守卫
           alpha_id IN (--reset 点名的 ID)
           AND ( funnel_status == '可提交候选'                  ← ★ R4/D23：守卫再收一档
                 OR (funnel_status == '改造候选'
                     AND status_source == 'prediction') )
         )

--reset 前置校验：点名的 ID 若处于保护态（待确认/已提交/提交失败）
                  或是「因 checks FAIL 归入的改造候选」（status_source='classify'），
                  明确报错并退出（退出码 3），★ 不静默跳过
按 --batch-size 分批，逐条：

  阶段一：get_self_correlation(alpha_id)
    max_corr is None（重试耗尽） → prediction_result = 'pending'
                                   funnel_status 保持「可提交候选」+ is_pending_flag = 1
                                   继续下一条（不阻塞其余候选）
    max_corr >= threshold        → prediction_result = 'fail'
                                   funnel_status = '改造候选'，status_source = 'prediction'
                                   ★ 不调用 prod 接口（短路）
    max_corr <  threshold        → 进入阶段二

  阶段二：get_prod_correlation(alpha_id)
    同上三分支；两路均低于阈值 → prediction_result = 'pass'
                                 funnel_status = '待确认'，status_source = 'prediction'

每条结论立即写库并提交事务 → 任意时刻中断，已完成部分不丢，重跑自动跳过
```

**「待定」的重跑路径（R2 新增，D15）**：`pending` 是**暂时**状态（平台侧异步计算未完成），但原设计的候选集只取 `prediction_result IS NULL`，被标 `pending` 的记录从此不再自动进入候选集，唯一出路是 `--reset` 逐个点名——而要拿到这些 ID 又得先能按状态查询。两处叠加会让几十上百条待定记录只能靠手写 SQL 处理。`--retry-pending` 与 `report --status` 各开一个口子，闭合这条运维路径。

**守卫为什么要收到 `status_source`（R4 新增，D23）**：「改造候选」有两类来源。`status_source='prediction'` 的是因相关性判死，重新预判合理；`status_source='classify'` 的是因 **checks FAIL**——它重新预判若通过会变成「待确认」并进入提交清单，于是一条 checks 未达标的 Alpha 排队等提交。平台侧大概率会拒，但这条路径不该由本地放行。`status_source` 是 NOT NULL DEFAULT 列，无 NULL 风险。

**`--reset` 的括号与守卫（R3 新增，D18）**：R2 版把 `--reset` 分支写在 `OR` 之后且无括号——按 `A AND B OR C` 的结合律，点名的 ID 会**绕过 `funnel_status == '可提交候选'` 前提**直接进候选集。点到一条「已提交」的 ID，预判会照跑并可能把它改写为「待确认」，进入下一次提交清单被**二次 POST**——直接污染唯一的不可逆动作。这与 §4.3 精心设计的保护态排除自相矛盾：同一批保护态，分流碰不得、预判却能碰。修法是补括号 + 限定适用状态 + 点名保护态时**明确报错**（静默跳过会让 Owner 以为重置成功了）。

**状态来源标记（R2 新增，Q5 答复）**：预判改写 `funnel_status` 时同步写 `status_source = 'prediction'`。原因：此时该记录的 `classify_*` 字段仍是上一次分流的结果（一份「可提交候选」的理由），与新状态不再对应。有了来源标记，报告即可区分「因 checks 归入改造候选」与「因相关性归入改造候选」（§4.5），两者的后续处置完全不同——前者改表达式可能有救，后者要换思路。FAIL 卡点分布不受污染：这类记录的 `gate_fails` 为空列表，展开后对聚合无贡献。

**短路的依据**：Demo 的 `brain-calculate-alpha-selfcorrQuick` skill 明确记载「self-corr > 0.7 则 prod-corr 必然 > 0.7」（`demo-code-deep-dive.md` §5 重点 2）。self 超阈即可直接判死，无需再查 prod。这把最坏情况下的平台调用次数**减半**，且不偏离 PRD #6 的「self/prod 相关性接口」路径。

阈值与来源写入每条 `prediction_reason_json`（§2.5）。v0.1 默认 `{"value": 0.7, "source": "convention_demo"}`，可经配置改为 `manual`；若日后探明平台返回该项 limit，改为 `platform` 而不动上层逻辑。

### 4.5 漏斗报告（PRD #7）

只读，纯 SQL 聚合，三块内容：

1. **各状态数量**：按 §3.1 七态分组计数（不含「未回测」——v0.1 无数据源）；「改造候选」**按 `status_source` 拆两行**显示（`classify` = 因 checks FAIL / `prediction` = 因相关性超阈），两者后续处置不同（R2/Q5）
2. **FAIL 卡点分布 TOP 榜**：从 `classify_reason_json.gate_fails` 展开，按 check 名聚合出现次数与平均 gap
3. **携带未判定门槛类 check 的候选数（A12）**：`non_gate` 中含 `ERROR` / `PENDING` 的「可提交候选」条数。CLUSTER_TEST 全样本为 ERROR，若它日后被证实是硬门槛，当前分流整体偏乐观——提交机会稀缺，这个数字必须对 Owner 可见
4. **待定条数**：`is_pending_flag = 1 **AND funnel_status = '可提交候选'**` 的记录数（R4/Q7——限定后一条件，避免把重算为淘汰候选的记录仍计入待定并提示重试），附一句提示可用 `precheck --retry-pending` 重试

`report --status <状态>` 输出该状态的**记录清单**（alpha_id / 表达式 / 理由摘要），承接 PRD #3「可按漏斗状态查询」在 CLI 层的落点，也是 `--reset` 取 ID 的来源（R2/D15）。

### 4.6 提交（PRD #8）—— 唯一不可逆动作

```text
submit --dry-run:
  清单 = funnel_status == '待确认' 的全部记录（PRD D8 口径）
  指纹 = sha256("\n".join(f"{alpha_id}:{prediction_result}" for 按 alpha_id 升序))
  打印清单 + 指纹 → 退出。★ 提交接口零调用（可断言）

submit --confirm <fingerprint>:
  重新计算当前清单指纹
  不匹配 → 退出码 4，拒绝提交（清单内容已变，确认失效）
  匹配 →
    ⓪ 前置检查：库中若存在 submit_result = 'in_flight' 的记录
       → 不进入提交流程，退出码 6，提示「存在 N 条待核对记录，请先跑 submit --reconcile」  ← ★ R3/D19·N11
    ① 先落「意向快照」：清单全量 + 指纹 + 确认留痕，逐条结果字段留空   ← ★ R2/Q6
       ★ 写盘失败（磁盘满 / 权限 / 目录缺失）→ 立即终止，退出码 1，不进入提交循环（R3/N12）
    ② 逐条提交，每条三步：
         a. 写 submit_result = 'in_flight' 并提交事务      ← ★ R2/N8 意向标记
         b. POST /alphas/{id}/submit
         c. 回写结果并提交事务
            成功：funnel_status = '已提交'，submitted_at，submit_result = 'success'
            失败：funnel_status = '提交失败'，submit_error = 原因原文（不吞异常）
    ③ 全部完成后**原地更新**同一快照文件，补齐逐条结果
    ④ 终端输出：「快照已写入 data/snapshots/xxx.json（不入 git，建议异地备份）」  ← R2/N10
```

**不可逆动作的状态歧义窗口（R2 新增，DevOps N8）**：原设计的「每条独立事务」只保证了中途失败不影响已完成条目，没有覆盖「POST 已成功、写库前进程死亡」这一窗口——该条平台侧已提交，本地仍是「待确认」，重跑会**再次 POST 同一个不可逆动作**，而平台对重复提交的行为无任何记录（`brain-platform-facts.md` 未覆盖）。

采用意向标记方案：提交前先写 `in_flight` 并落库，再 POST。重跑时遇到 `in_flight` 的记录**一律不自动重提**，退出并提示人工核对。代价是每条多一次写库，换掉一个不可逆动作的状态歧义，值得。

**`in_flight` 的解除路径（R3 新增，D19 + DevOps N11 合并处置；取数路径于 R4 修正）**：R2 版只写了「转人工核对」，而当时给的核对手段（增量同步反查）**本身就不成立**——见下方 R4 修订说明；更根本的是，**反查之后没有任何 CLI 能把状态收敛回去**——同步只创建不覆盖派生数据（§4.2 `DO NOTHING`），那条记录会永远停在 `in_flight`，每次重跑 `submit` 都撞上同一条并退出，`submit` 被永久锁死。而 v0.1 没有任何改库命令，Owner 只能手写 SQL——恰好是在一次不可逆动作的中断现场。

补一条命令闭合它：

```text
submit --reconcile:
  对全部 submit_result = 'in_flight' 的记录，逐条直查平台详情：   ← ★ R4 修订（D21/N14）
    detail = client.get_alpha(alpha_id)          # GET /alphas/{id}，不经本地库、不经水位
    ★ 同一事务内先用 detail UPSERT alpha 表（stage / date_submitted / raw_json /
      fetched_at）——详情已在手，零额外请求（R4 定稿前补，D24）
    detail.stage == 'OS'  → funnel_status = '已提交'，submit_result = 'success'，
                            submitted_at 取 detail.dateSubmitted
    detail.stage == 'IS'  → 回退 funnel_status = '待确认'，清空 submit_result
                            （提交未达成，可重新走确认流程）
    查询失败（网络 / 429 / 5xx）→ ★ 保持 in_flight 不动，不猜测、不收敛（R4/N15）
  → 原地补齐对应快照的逐条结果（补上中途死亡时缺失的步骤 ③）
  → 输出收敛明细 + 未能收敛清单供 Owner 核对
  → 仍有 in_flight 残留时以退出码 6 退出；全部收敛则 0
```

自动收敛是安全的：判据来自平台自身的 `stage`，不是本地推测；两个方向都不产生新的不可逆动作（OS 方向只是把既成事实记录下来，IS 方向只是退回确认前）。

> **R4 修订（D21 / N14）——R3 版的取数路径不成立，且失效方向是危险的。**
>
> R3 写的是「先 `sync --incremental --stage OS` 刷新平台字段」。但增量同步按 `dateCreated > 水位` 拉**新增**，而提交只改 `stage` 与 `dateSubmitted`、**不改 `dateCreated`**——已入库记录永远进不了增量集合。§4.2 本身就写着「已入库 Alpha 的平台字段刷新由全量重拉或预判回写承担，**不属增量职责**」，而 `--reconcile` 要刷新的恰恰是一条已入库记录的 `stage`。**同一份文档里自相矛盾。**
>
> 后果：收敛读到库里的旧值 `IS` → 判「提交未达成」→ 退回「待确认」→ 下一轮 `submit` **再次 POST 同一个不可逆动作**——正是这整条机制存在的理由。N8 的原始缺陷至少会**停下来要人工核对**（fail-safe）；R3 的写法会在**无人参与时自动误判并重提**（fail-dangerous）。同一个漏洞第二次出现比第一次更危险。
>
> 另：R3 版在当时的 `BrainClient` 契约下**根本无法实现**——契约里没有任何按 `alpha_id` 查单条的方法。R4 补 `get_alpha`（§3.1）后闭合。
>
> **判据独立性是恢复路径的必要性质**（N14 ③）：直查让收敛完全绕开本地库与水位逻辑。恢复路径不该依赖那条可能已经出问题的常规写入链——这一条比「修好这个 bug」更值得记住。

**为什么收敛要顺带 UPSERT `alpha` 表（D24）**：`get_alpha` 拿回的是完整详情，若只写 `alpha_state`，收敛为「已提交」后 `alpha.stage` 仍是本地旧值 `IS`，与 `funnel_status` 不一致，要等下一次全量同步才被刷新。当前所有逻辑（报告、清单、适用域）都按 `funnel_status` 走，故无功能影响——但**详情已在手、零额外请求**，让两张表当场自洽比留一个已知的不一致更好。注意这**不违反字段分层**：写的是平台原始字段，用的是刚从平台取回的权威数据，与 §4.2 同步写 `alpha` 表是同一性质。

**快照与回写的先后（R2 新增，Q6 答复）**：**先落意向快照，再逐条提交，最后原地补齐结果。** 理由是快照的定位——它是这个动作的**唯一证据**（ADR-0003 因此把 `data/snapshots/` 列为受保护路径）。若等全部提交完成才落盘，恰好在提交过程中死亡时会一份证据都没有，而这正是最需要证据的时刻。写两次同一文件不损害其证据性：文件名由指纹决定、内容单调补全，且与库中的 `in_flight` 标记互为印证。

指纹覆盖 `alpha_id` 与 `prediction_result` 两项：清单增删条目、或某条预判结论变化，指纹即变、确认即失效。快照内容：时间、指纹、清单全量、确认留痕、逐条提交结果。

**三重兜底**（dry-run 零调用 / 指纹绑定 / 快照落盘）全部可自动断言，对应 PRD #8 的五项测试点。

### 4.7 凭据处理（PRD #9）

```text
路径：$BRAIN_CREDENTIALS_PATH 或 <项目根>/.brain_credentials（L1）
格式：JSON 数组 [email, password]
缺失 / 格式错 / 认证失败 → 明确报错 + 退出码 2，不打印任何凭据内容
```

红线：凭据只入内存 `Credentials` 实例；不写回任何文件；不进日志；HTTP 层的 `Authorization` 头与 session cookie 不落盘。日志采用**白名单式**记录（只记方法名、alpha_id、状态码、耗时），而非「记录全部再脱敏」——后者一旦漏一处就泄露。

**两道防线（R2 补充，N6）**：白名单式日志只管得住**显式**的日志调用，管不住 `repr()` 经由未捕获异常的 traceback、`logging.exception`、调试器打印局部变量等路径泄露。因此 `Credentials.password` 声明 `field(repr=False)`（§3.1），从数据结构层面封堵——这是契约的一部分，写在接口契约里实现会话才不会漏。

`#9` 的结构化扫描断言（测试不读凭据明文）由此有了确定的断言对象：

- 扫描目标：`data/logs/*.log`（§1.4 定位）+ `data/inventory.db`
- 断言内容：不出现 `password` / `credentials` 字段名与 Basic 认证串特征；`"password" not in repr(credentials_instance)`
- 测试自身不读取 `.brain_credentials` 内容

## 7. 风险和取舍

### 7.1 风险

| # | 风险 | 影响 | 处置 |
|---|------|------|------|
| R-1 | **预判耗时可能达数小时**。相关性接口最坏约 **80 秒等待**/条（R3 订正：`max_retries=5` 时 5 次尝试之间只有 4 次 `sleep(20)`，且无退避递增，见 `platform_functions.py:1020-1036`；另加 5 次请求往返）。两阶段短路后，N 条候选的最坏总耗时约 N×80 秒（全部 self 即判死）到 N×160 秒（全部走完两阶段）。若可提交候选有 500 条，最坏 11~22 小时 | 高——直接决定 #6 在真实库存上是否跑得完 | 设计侧已尽力：两阶段短路减半、分批、断点续跑、`--limit` 分次。**但这是平台速度决定的下限，设计无法再压缩**。提请 Owner 知悉：先跑 `classify` + `report` 看候选规模，再决定预判范围（可先按 gap 排序只预判最优的 N 条）。若 Owner 认为需要收窄 v0.1 范围，走 Change Note |
| R-2 | **`count` 字段本身可能被封顶**（实测未提交恰为 10000） | 中——影响 §4.1 窗口级对账的左值可信度 | 叶子窗口的 `count < 9000`（低于疑似上限），不触及封顶；`count >= 9000` 的窗口一律细分。逻辑自洽。若某窗口细分到秒级仍 ≥ 阈值，`status=partial` 留痕 |
| R-3 | **提交前检查触发端点是否存在，仍未被证伪**（PRD 风险 2 要求设计阶段查证） | 中 | 见 §7.3 查证结论 |
| R-4 | **平台撤回能力未知**（PRD 风险 3） | 中 | 见 §7.3 查证结论 |
| R-5 | 平台并发上限（Demo 的 `ace_lib` 证实存在并发限制需退避） | 低 | v0.1 全串行，天然规避。`RateLimitError` 退避作为兜底 |

### 7.2 关键取舍

| 决策 | 选择 | 备选 | 为什么不选备选 |
|------|------|------|----------------|
| 存储 | SQLite | JSON 文件 / DuckDB / Postgres | JSON 文件无事务，断点续跑与并发写不安全；DuckDB 长于分析、短于事务写入；Postgres 引入服务端运维，违背「本地运行」定位 |
| 原始字段 | 只存 `raw_json` + 抽索引列 | 每字段建列 | 拆列造成同一数据两处存储，与「平台原始不可变、单一真源」冲突；解析成本在手动命令下可忽略 |
| 派生数据 | 独立表 | 同表加列 | 独立表让「同步不触碰派生」由 schema 保证，而非靠代码纪律；PRD 的字段分层是硬约束，值得用结构来兜 |
| 预判路径 | 平台相关性接口 + 两阶段短路 | 本地 PnL 快算（`selfcorrQuick`） | PRD #6 定稿口径写明「self/prod 相关性接口」；本地快算需先拉全部对照集 PnL，v0.1 引入新数据面与新算法，成本与风险都更高。已在 §6.2 留好换实现的边界，v0.2 再评估 |
| 预判断点 | 复用 `prediction_result` 非空 | 独立进度表 | 「已有结论就跳过」与「断点续跑」本是同一件事，两个状态载体必然漂移 |
| CLI 框架 | argparse | click / typer | 五条子命令，标准库够用，少一个依赖 |
| 数据校验 | dataclass | pydantic | 外部输入只有平台 JSON，校验点集中在客户端层 |

### 7.3 设计阶段查证结论（PRD 风险 2 / 风险 3）

**风险 2（提交前检查触发端点）——查证范围内未发现，结论维持 PRD 方案 B。**

已查证的证据面（R3 订正措辞，明确各条的查证主体）：
