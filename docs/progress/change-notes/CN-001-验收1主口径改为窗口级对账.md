## 背景

PRD 定稿的验收 #1 主口径为：

> **主口径（通过条件）**：本地去重条数 == 按 dateCreated 时间窗切片穷尽求和的去重条数，且连续两次执行结果一致。

该口径是 PRD R1 阶段为消除「自证循环」（Architect A4 / Developer D2、D6）而反复收敛的结果，方向正确。设计阶段把它落到具体实现时，发现按**字面**实现仍不可用。

## 问题描述

两个独立原因：

1. **恒等，无判别力。** 时间窗切片是设计中唯一的写入路径（§4.1）。「本地去重条数」正是切片写入的结果，与「切片求和的去重条数」必然相等——无论分页是否有缺失，该断言恒为绿。这是 R1 A4 指出的自证循环换了个位置复现。
2. **会误判红。** 设计为规避平台 `dateCreated>` / `dateCreated<` 双开区间导致的边界记录静默丢失，相邻窗口重叠 1 秒（详见 ADR-0002）。重叠使 `Σ 各窗口 fetched_count > 本地去重行数`。按 PRD 字面写「两数相等」的断言，在实现完全正确时反而判红。

Developer 在设计 R1 Review 中提出该问题（D12），并指出实现会话会面对 PRD 与设计两个不同的期望值，隔离会话无从选择。

## 处理方式

验收 #1 的**主口径（通过条件）**由：

> 本地去重条数 == 按 dateCreated 时间窗切片穷尽求和的去重条数，且连续两次执行结果一致

变更为：

> **主口径（通过条件）**：每个叶子时间窗满足「实际拉取的去重条数 == 平台对该窗口报告的 `count`」，且连续两次全量同步本地行数一致。
> **交叉验证（留痕，不作通过条件）**：不带任何时间窗查询得到的全局 `count` 与本地行数比对并留痕——该值可能被平台计数上限截断，是诊断信号而非判据。
> **诊断项（断言留痕存在，非断言两数相等）**：offset 分页穷尽条数与本地行数不一致时，记录「offset 封顶」留痕。

其余部分（诊断项原文、验证方式、验证入口）不变。

**为什么新口径更强**：左值 `reported_count` 来自平台对该窗口的独立报告，不由本地写入路径产生。窗口内分页若有缺失，左右值立即不等——这正是原口径查不出的失败模式。
